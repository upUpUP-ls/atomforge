# AtomForge 项目说明

> 本文档说明 AtomForge Demo 的实现思路、完成程度与后续规划，供评审与交接使用。  
> 产品定位：对齐 [Atoms.dev](https://atoms.dev/) 体验的多 Agent 应用生成 Demo。

---

## 1. 项目概述

AtomForge 是一个 **可登录、可持久化、可端到端演示** 的全栈 Web 应用：用户用自然语言描述需求，后台由 Mike → Emma → Bob → Alex 四个 Agent 协作生成计划与代码，前台以 **Alex 为唯一对话入口**，用户在左侧查看实施计划与工作流程，在右侧 Preview 中验证生成结果。

**技术栈：** Next.js 16 · TypeScript · Tailwind + shadcn/ui · Prisma 7 + SQLite/Turso · NextAuth v5 · SSE · OpenAI（可选）

**本地访问：** `npm run dev` → http://localhost:3000

**在线 Demo：** [https://atomforge-m8bt.vercel.app](https://atomforge-m8bt.vercel.app)（部署说明见 [DEPLOY.md](../DEPLOY.md)）

## 2. 实现思路与关键取舍

### 2.1 部署驱动：单体全栈，而非前后端分离

本项目 **需要自己部署、对外提供可访问的在线 Demo**，架构选型首先服从「部署简单、一人可维护」这一目标，因此 **没有采用前后端分离**（独立 React SPA + 独立 Node/Java API 服务），而是采用 **Next.js 单体全栈**：

| 前后端分离 | 当前方案（Next.js 单体） |
|------------|---------------------------|
| 前端、后端两个仓库或两套构建 | **一个仓库、一次 `npm run build`** |
| 需分别部署（如 Nginx + 静态资源 + API 服务器） | **Vercel 等平台一键部署**，环境变量集中配置 |
| 跨域、Cookie、SSE 流式需额外处理 | **同域 API Route + SSE**，Session / 鉴权链路短 |
| 本地开发常起两个进程 | **`npm run dev` 单命令** 跑通全链路 |

**取舍：** 牺牲「前后端团队独立迭代、技术栈完全解耦」的灵活性，换取 **部署面最小、Demo 交付成本最低**。Agent 流水线、数据库、鉴权、Preview 页面都在同一进程内协作，适合 Demo 与评审场景；若未来产品化、团队扩大，再考虑拆出独立 BFF 或 Agent 微服务。

在单体内部，仍用 **按域分层** 保持代码清晰：`app/` 只做路由，业务在 `features/`（auth / projects / agents），基础设施在 `lib/`（db / auth / ai）。详见 [ARCHITECTURE.md](../ARCHITECTURE.md)。

### 2.2 Agent 编排：SOP 流水线 + 分阶段执行

| 模式 | 步骤 | 用途 |
|------|------|------|
| `plan-only` | Mike | 生成实施计划，等待用户批准 |
| `build` | Emma → Bob → Alex | 计划批准后后台构建 |
| `alex-only` | Alex | 用户对话迭代 |
| `full` | 四 Agent 连续 | CLI 测试（`npm run test:agents`） |

**取舍：** 对齐 Atoms「先看计划、再构建」的体验，将流水线拆成 **计划阶段** 与 **构建阶段**，而不是一次性跑完四个 Agent。用户主流程可控，但实现上多了 `PipelineRun` 子资源与 SSE 状态机。

### 2.3 前台 UX：Alex 单入口，子 Agent 不 dump 全文

正式 Atoms 中，用户主要与 **Alex（Engineer）** 交互，关注 **实施计划** 与 **工作流程步骤**，而非 Emma 的 PRD、Bob 的架构长文。

**实现：**

- 对话区只展示 Alex 状态摘要 + 计划卡片 + 可折叠「工作流程（已处理 N 步）」
- Emma / Bob 的输出写入数据库作为 artifact，供后台与代码仓库导出使用，不堆在对话里
- Fallback 模式下通过 `mock-workflow.ts` 模拟「读文件 / 写文件 / 跑命令」等细粒度步骤

**取舍：** 牺牲「四个 Agent 各说各话」的展示完整性，换取更接近真实产品的信息密度与可读性。

### 2.4 API 设计：REST 资源化 + 统一响应

早期 RPC 风格接口（如 `/api/agents/run`）已重构为：

- `POST /api/projects/:id/pipeline-runs` — 创建流水线
- `GET  .../pipeline-runs/:runId/events` — SSE 事件流
- `GET/PUT /api/projects/:id/session` — 对话与工作流持久化
- `GET /api/health/ai` — AI 模式健康检查（公开，见 [API.md](./API.md)）
- 统一 `{ data }` / `{ error: { message } }` 响应体

**取舍：** REST 语义更清晰、便于文档化（见 [docs/API.md](./API.md)），但客户端需维护 EventSource 连接与 runId 生命周期。

### 2.5 无 API Key 仍可完整 Demo：Fallback 双轨

| 有 `OPENAI_API_KEY` | 无 Key（Fallback） |
|---------------------|-------------------|
| LLM 流式生成计划 / PRD / 架构 / HTML | 按 prompt 关键词匹配预置模板 |
| Alex 输出需从 Markdown 中提取 HTML | 直接流式输出完整单页 HTML |
| 工作流程步骤较少 | 模拟 14+ 步细粒度工作流 |

**取舍：** Demo 交付不依赖外部 API 配额与网络；代价是生成结果多样性有限，且代码形态以 **单文件 HTML** 为主，而非真实 Atoms 的多文件 React 仓库。

### 2.6 AI 模式可验证（评审自证）

除配置 `OPENAI_API_KEY` 外，项目提供 **可观测** 手段，避免「代码接了 OpenAI、线上却在走 Fallback」的质疑：

| 方式 | 说明 |
|------|------|
| **公开接口** | `GET /api/health/ai` 返回 `{ mode, model, configured }`，无需登录、不暴露 Key |
| **UI 标签** | 工作台侧栏、项目编辑器顶栏显示 `AI: OpenAI · gpt-4o-mini` 或 `AI: Fallback 模板` |
| **行为对照** | Fallback 对非常规 prompt 会命中固定模板；LLM 会按描述定制内容（见 [API.md](./API.md)） |

**取舍：** 增加一个只读 health 路由与前端 Badge，换取评审与运维 **零后台权限** 即可验证 AI 模式。

### 2.7 持久化策略

| 数据 | 存储 | 说明 |
|------|------|------|
| 用户 / 项目 | Prisma `User` / `Project` | 注册登录、项目列表 |
| Agent 产物 | `Artifact`（plan / prd / architecture / code） | 版本递增 |
| 流水线记录 | `PipelineRun` | mode、status、planOverride |
| 左侧会话 UI | `Artifact`（workflow / chat） | JSON 序列化，刷新可恢复 |
| 生成应用内数据 | 视模板而定 | Todo 等用 localStorage；销售页等为静态数据 |

**取舍：** 会话 UI 复用 `Artifact` 表而非单独建 `ChatMessage` 表，减少迁移成本；JSON blob 查询能力弱，但 Demo 规模足够。

### 2.8 代码导出：ZIP 代码仓库，而非单 HTML

下载按钮导出 `{项目名}.zip`，包含 `public/`（拆分后的 html/css/js）、`docs/`（计划 / PRD / 架构）、`README.md`、`package.json`。

**取舍：** 更接近「下载仓库」的产品语义；当前 LLM/Fallback 产物仍是单 HTML 源，zip 内结构是 **演示级脚手架**，不是真实 Vite/React 工程。

## 4. 后续扩展与优先级

若继续投入，建议按 **「先能对外演示 → 再逼近 Atoms 真实体验 → 再工程化」** 排序。

### P0 — 必须做（阻塞 Demo 交付）

| 任务 | 理由 | 状态 |
|------|------|------|
| **Vercel + Turso 部署并填写在线链接** | 满足「可测试在线访问」硬性要求 | ✅ [已上线](https://atomforge-m8bt.vercel.app) |
| **部署后全流程冒烟** | 注册 → 建项 → 计划 → 批准 → Preview → 导出 → 刷新一致性 | 建议评审前再跑一遍 |
| **同步 README / 说明文档** | 导出方式、在线链接、体验路径与实现一致 | ✅ 已同步 |

### P1 — 高价值（显著提升「像 Atoms」）

| 任务 | 理由 | 预估 |
|------|------|------|
| **接入并调优 OpenAI 生成** | 真正 LLM 驱动，脱离固定模板 | 1～2 天 |
| **Alex 多文件项目生成 + 文件树 Preview** | 对齐 Atoms 核心差异（代码仓库而非单 HTML） | 3～5 天 |
| **自然语言批准计划** | 输入「批准计划」触发 build，与正式产品一致 | 0.5 天 |
| **LLM 模式下的 workflow_step 生成** | 从 Agent 输出解析或工具调用事件，替代纯 mock | 1～2 天 |

### P2 — 体验打磨

| 任务 | 理由 |
|------|------|
| 项目页标题可编辑、历史 run 列表 | 多轮迭代可追溯 |
| Dashboard「发现」Tab 内容 | 对齐 Atoms 首页丰富度 |
| 深色主题 / 响应式细节 | 移动端与视觉 polish |
| 生成物 CI 检测（build 是否真的过） | 提高 Preview 可信度 |

### P3 — 工程与规模化

| 任务 | 理由 |
|------|------|
| E2E 测试（注册 → 生成 → 导出） | 防回归 |
| 队列化流水线（Redis / Inngest） | 避免单进程 `runningProjects` 限制 |
| 多租户 / 团队协作 | 产品化方向 |
| 积分与用量统计 | 对齐 Atoms 商业模型 |

### 优先级判断逻辑

```text
在线链接（P0）> 真实 LLM + 多文件生成（P1）> UX 细节（P2）> 架构升级（P3）
```

原因：

1. **在线 Demo 已部署**，评审可直接打开 [https://atomforge-m8bt.vercel.app](https://atomforge-m8bt.vercel.app) 验证；Fallback 不能证明 AI 生成能力，需结合 `/api/health/ai` 与 Key 配置判断。
2. **Fallback 能演示流程，但不能证明 AI 生成能力**；有 Key 且生成质量可感知，才是差异化。
3. **多文件仓库**是用户心智中「Atoms = 生成代码项目」的核心，优先级高于 Dashboard 美化。
4. 队列、计费等适合产品化阶段，Demo 阶段投入产出比低。

## 5. 快速体验路径

### 在线 Demo（推荐评审使用）

打开 [https://atomforge-m8bt.vercel.app](https://atomforge-m8bt.vercel.app)：

1. 注册账号  
2. Dashboard 输入「帮我做一个前端销售网页」或 Remix 模板  
3. 等待计划生成 → 查阅实施计划 → **批准计划**  
4. 观察左侧工作流程步骤 → 右侧 Preview 交互  
5. 底部输入框让 Alex 迭代（如「改成深色主题」）  
6. 点击下载 → 获得 ZIP 代码仓库  
7. **刷新页面** → 确认左侧流程与计划仍一致  

### 本地开发

```bash
cd atomforge
cp .env.example .env   # 配置 NEXTAUTH_SECRET 等
npm install
npm run db:migrate
npm run dev
```

1. 打开 http://localhost:3000 → 注册账号  
2. Dashboard 输入「帮我做一个前端销售网页」或 Remix 模板  
3. 等待计划生成 → 查阅实施计划 → **批准计划**  
4. 观察左侧工作流程步骤 → 右侧 Preview 交互  
5. 底部输入框让 Alex 迭代（如「改成深色主题」）  
6. 点击下载 → 获得 ZIP 代码仓库  
7. **刷新页面** → 确认左侧流程与计划仍一致  

### 验证 AI 模式（本地 / 线上）

```bash
# 无需登录
curl https://atomforge-m8bt.vercel.app/api/health/ai
# 本地：curl http://localhost:3000/api/health/ai
```

- `mode: "openai"` 且 `model: "gpt-4o-mini"` → 真实 LLM 已启用  
- `mode: "fallback"` → 未配置 `OPENAI_API_KEY`，走预置模板  
- 登录后查看侧栏或项目页顶栏的 **AI:** 标签，应与接口结果一致
